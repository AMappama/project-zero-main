# CRM 牵线宝

这个包是成交之后的履约账，并带一个红娘用的工作台。一笔订单只留一条服务实例。计划开始日、开始、结束、总结束，以及活动、恋爱指导、一对一、形象的总量和已用，都写在这一条上。已用从 0 开始，这一期不扣已用。

没有单独的服务期表、次数表、暂停历史表、过期池表，也没有诚意库和课次。会员身份按固定顺序计算。`members.member_type` 只是同一次改实例事务里回写的缓存，没有人手修改的入口。服务库、过期 VIP、即将到期、处理中都是查询。

到期通知写在 `close_vip_contract`，这一行不关单。开启成功会写一条 `ServiceStarted` 出站事件。

`order_facts` 只保存履约要看的订单事实（是否付清、合同是否审核通过、时长、四类次数、退款是否完成）。`deal_assignments` 是成交域的销售/邀约归属投影，用来在开启时做兼容清理，以及记录关单后的销售/邀约领取。它不是服务库。

## 安装

Web 仍是一个 Node 进程（API + 工作台）。业务库走 **MySQL 协议**（`mysql2`），登录会话走 **Redis**。

有 Docker 时：

```bash
docker compose up -d
npm install
npm run dev
```

`docker-compose.yml` 起的是 `mysql:8.4` 和 `redis:7`，账号与 `.env.example` 一致。

这台机器没有 Docker。当前本地进程是 **MariaDB 11.4**（MySQL 协议，库和用户都是 `fulfillment`）和 **Redis 3**，文件在 `.tools/`（不进版本库）。下次开机后先执行：

```powershell
powershell -File scripts/start-local.ps1
npm run dev
```

## 工作台

```bash
npm run dev
```

浏览器打开 `http://127.0.0.1:47291`。服务绑在 `0.0.0.0`。端口可用 `PORT` 改，不要用 3000、5173 或 8080。

每次启动会 **重置 MySQL 库表**（`DROP` + 建表 DDL），并在演示日 2026-09-30 用现有写入铺开样本。会话在 **Redis**（默认 `redis://127.0.0.1:6379`）。进入工作台先登录。两个账号是：林晓只有红娘，苏衡是红娘加审核人。红娘看到待判断和例外，并能确认这些动作，不能通过或驳回。苏衡一次登录两边都看得到，也能通过或驳回。

待判断里的推荐草稿，按当前登录红娘的服务库现查：每位在库会员配一位库内客人，客人不是本人，也还没有推荐事实，不打分。确认之后才写推荐事实。服务库、约会、过期 VIP 都是当天查询出来的名单，点一行进原来的二级页，返回回到来处。

第一屏仍是服务跟进的版式：左侧导航、深色汇总、待判断 / 例外 / 审核。没有权限的那一块不出现。审核列表只给有审核权限的账号。

## 租户开关

没有配置行时按默认值：

- `auto_start_service` 默认开。四项满足就由系统开启。关掉之后停在待启用，由人调用同一次 `openService` 确认开启。
- `auto_draft_close_on_in_love` 默认关。约会结果为恋爱时只写「关单建议」，不建关单申请。打开后才起草，仍然不自动审核。
- 兼容清理默认开。开启时停用该会员仍有效的销售/邀约归属，避免和在服归属并存。关掉时不清理，`listDualOwnership` 把两边都有效的人标出来。

## 写入

每次动作一个事务。

- 指定服务人，或按门店 matchmanager、店长、总监的顺序自动写下一位。三个角色都没有就不开启，结果里是「缺服务人」。落到店长或总监名下的，`listStaffingExceptions` 标成高优例外。
- 开启只看四项：订单已 payable 或 paid、合同 `check_status = 1`、已经有服务人、计划开始日不是将来。外加租户是否允许自动开。不检查实名。开启写成启用中，写入起止和四类总量，已用为 0，成熟度记为新升级，审计记下 `opened_by` 和四项快照，并写出 `ServiceStarted`。不写系统节点小记。
- 准备推荐草稿只写任务，不写推荐事实。红娘确认后才写推荐，并把草稿结案。
- 确认约会或见面结果。日常联系可以另写人工小记，系统动作不写。
- 发起暂停、赠送、关单。关单原因直接写文字，包括「放弃」和「共识退费未解约」。
- 关单一审只把申请改为待二审。两级都通过才把实例改为完成，并写上是否同意、原因、关单人、关单前服务人。同时停用当前服务人，成熟度记为已关单。
- 暂停通过只把实例改为暂停，结束日和总结束日不动。恢复时新的结束日 = 恢复日 + 暂停时还剩的服务月。例：六个月服务在第二个月最后一天暂停，还剩四个月，新结束日是恢复日再加四个月。
- 赠送通过只延长结束日或总结束日，或增加某一类总量。已用不动。申请上留下改前改后。赠送和暂停都是一次审核。
- 到期函插入一行，不改实例。签署回调只改这一行的状态。总结束日到了会起草关单，不自动通过。
- 退款完成把实例改为失效，并停用这笔订单上的服务归属。失效不是完成。

成熟度只由系统写成三个值：新升级、暂停、已关单。中间档留空，也不用来起草关单。

## 查询

身份按这个顺序，命中即停：任一启用中是 VIP；否则任一暂停是暂停（高于另一笔待启用）；否则任一待启用是待开启；否则按订单时间最新的一笔，完成是过期 VIP，失效是退费。没有实例是普通。

服务库是当前服务人名下、待启用、启用中或暂停的会员。红娘领取过期会员后，会写下该红娘为当前服务人，人出现在这位红娘的服务库。

过期 VIP 必须同时满足：有已完成的服务实例、有已通过且四项齐全的关单申请、当前没有有效服务归属。关单后的销售/邀约领取写在成交域投影上，人离开过期 VIP，也不进入服务库。成交时留下、开启前就有的销售/邀约归属不算这次领取。

处理中是还没走完的申请。关单的待审和待二审都算。赠送、暂停的待审算；审核通过之后不算。

## 恢复日怎么加

剩余月数在暂停通过时记在暂停申请上。服务月按日历月计，不满一个月不按天折算。暂停隔了多久才恢复，都不改这个剩余月数，也不把暂停天数加回原来的结束日。
