成交之后，红娘看到的不是订单系统，是一本履约账。

你打开的是服务跟进，不是成交台

想象你用浏览器打开 http://127.0.0.1:47291。先登录，再看到左侧五栏：服务跟进、服务库、约会、审核列表、过期 VIP。

这个包只负责成交之后。一笔订单只留一条服务实例：什么时候开始、什么时候结束、活动 / 恋爱指导 / 一对一 / 形象各有多少次。这一期已用从 0 开始，还不扣次数。

腕带上没有姓名，只有一串随机号

登录成功后，浏览器拿到的是一枚 Cookie。真正的账号编号放在 Redis 里。退出时删掉这条记录，腕带立刻作废。

代码 
export async function signIn(accountId: number) {
  const account = ACCOUNTS.find((item) => item.id === accountId);
  if (!account) return null;
  const token = randomBytes(18).toString("hex");
  const client = initRedis();
  await client.set(sessionKey(token), String(account.id), "EX", SESSION_TTL_SECONDS);
  return { account, token };
}
白话

登录函数。传入的是页面上点的那个账号编号。

在写死的两个账号里找。林晓是 1，苏衡是 2。

找不到就当没登录成功。

随机生成一串腕带号，不把姓名写进饼干。

连上 Redis。

把「腕带号 → 账号编号」存起来，并设过期时间。默认 7 天。

把账号信息和腕带号交还给调用方，再由接口写成 Cookie。

函数结束。

文件在 src/accounts.ts。跟 AI 说「加一个账号」时，要同时说：名单在 ACCOUNTS，会话仍走 Redis，不要新开一张用户表。

同一份名单，按权限裁成两个人看到的样子

服务跟进有三栏：待判断、例外、审核。后端先把三栏都算好，再按登录人剪掉没权限的那栏。所以林晓不是「审核坏了」，是审核被故意收成空列表。

代码 
function homeForAccount<T extends { judgement: unknown[]; exceptions: unknown[]; reviews: unknown[] }>(home: T, account: Account | null) {
  if (!account) return home;
  return {
    ...home,
    judgement: hasPermission(account, "红娘") ? home.judgement : [],
    exceptions: hasPermission(account, "红娘") ? home.exceptions : [],
    reviews: hasPermission(account, "审核人") ? home.reviews : [],
  };
}
