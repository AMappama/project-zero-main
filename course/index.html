点开工作台的那一秒

成交之后，红娘看到的不是订单系统，是一本履约账。

你打开的是服务跟进，不是成交台

想象你用浏览器打开 http://127.0.0.1:47291。先登录，再看到左侧五栏：服务跟进、服务库、约会、审核列表、过期 VIP。

这个包只负责成交之后。一笔订单只留一条服务实例：什么时候开始、什么时候结束、活动 / 恋爱指导 / 一对一 / 形象各有多少次。这一期已用从 0 开始，还不扣次数。

腕带上没有姓名，只有一串随机号

登录成功后，浏览器拿到的是一枚 Cookie。真正的账号编号放在 Redis 里。退出时删掉这条记录，腕带立刻作废。

代码 
export async function signIn(accountId: number) {
  const account = ACCOUNTS.find((item) => item.id === accountId);
  if (!account) return null;
  const token = randomBytes(18).toString("hex");
  const client = initRedis();
  await client.set(sessionKey(token), String(account.id), "EX", SESSION_TTL_SECONDS);
  return { account, token };
}

02

一笔订单，一本护照

服务期、次数、暂停历史都不另开抽屉。关键事实盖在同一本上。

护照只有一本，贴纸不能散落

出国你不会把签证、入境章、行程单分装进五个没编号的袋子。牵线宝也拒绝那些袋子：没有单独的服务期表、次数表、暂停历史表、过期池表，也没有诚意库和课次。

一笔订单对应一行服务实例。改期、暂停、赠送，都是改这一行，或在申请单上记下改前改后。

履约柜
order_facts成交域递过来的事实：付没付清、合同审没审过、时长、四类次数、退款
service_instances护照本身。一个订单号只能有一行
service_ownerships现在谁在服务这位会员。一个人同时只有一条有效归属

tasks还没盖章的草稿：推荐草稿、关单建议
recommendations已经确认的推荐事实。草稿确认之后才写到这里

一本护照都没有，普通人。

抄写员被一把锁看着

members.member_type 是缓存。数据库触发器规定：这列要变，必须先把 write_guard 拨到允许，写完再拨回去。

白话

先把分诊结果算出来。

把唯一一把锁拨到「允许抄写」。锁的编号永远是 1。

这时才能改会员身上的类型缓存。

立刻把锁拨回去。函数叫 refreshIdentityCache。

⚠
直接改 member_type 会被数据库吼回来

触发器的原文是「身份缓存只能由实例事务回写」。AI 若写一条裸的 UPDATE，库会拒绝。跟它说：改实例，让 refreshIdentityCache 去抄。

💡
服务库、过期 VIP、处理中都是查询

它们不是另存的一份名单。条件变了，下次查询结果就变。所以「名单怎么还在」通常是条件没变，不是缓存没刷新。

开启要过四道门

付清、合同、服务人、开始日。少一张，人就停在待启用。

登机口不看心情，只看四张牌

机场不会因为你「看起来像要飞」就放行。开启服务也只看四项，外加一个租户开关。不检查实名。

付

订单

付款状态得是 payable 或 paid。未付清，缺口写「订单」。

合

合同

contract_check_status 必须等于 1，也就是审核通过。

人

服务人

会员名下要有一条还有效的服务归属。没有就叫「缺服务人」。

日

计划开始日

计划开始日不能晚于「今天」。今天是演示日，不是墙上的日历。

暂停和赠送只审一次

暂停通过只把实例改成暂停，结束日先不动。赠送通过只延长结束日或增加某一类总量，已用不动。

恋

恋爱不等于关单

默认只写「关单建议」，不建申请。打开自动起草后才会起草，仍然不自动审核。

暂停像月票，不满一个月不算用过

服务月按日历月计。某一服务月只有在暂停日不早于该月最后一天时，才算走完。暂停了多久再恢复，都不把暂停天数加回原来的结束日。新的结束日 = 恢复日 + 暂停时记下的剩余月数。

6 个月 1 月 1 日开始。2 月最后一天暂停：走完 2 个月，剩下 4 个月。
恢复日 + 4 哪怕停了很久，剩下的仍是 4 个日历月，从恢复那天往后加。
已用不动 赠送和暂停都不改已用次数。这一期本来也不扣已用。
