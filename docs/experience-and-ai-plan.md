## 0. 术语速查

| 词 | 定义 |
|---|---|
| **情绪劳动** | 社会学概念（Hochschild, 1983）：为了完成工作，必须持续管理自己的情绪与表情。**红娘的核心产出就是情绪劳动**，工具目前是在放大它，而不是替她承担它。 |
| **被服务者** | 本产品的用户 = 红娘/匹配师。客户（会员）是**被服务的人**，不是软件的直接用户。这条区分是全部设计的起点。 |
| **情绪账户** | 比喻：红娘每天有一笔「情绪存款」。每次被迫理解术语、重新回忆细节、被系统指责，都在扣款；每次被系统记住、给她现成草稿、明确告诉她「你今天帮了谁」，都在存款。 |
| **ID 泄漏** | 把 `会员 105` 这类系统主键推到用户眼前。用户的注意力应该落在**人**身上，而不是数据库的自增列。 |
| **两段式摘要** | 一句话（≤12 字，扫读）+ 可展开正文（完整语境）。长文案不做主视觉。 |
| **硬约束 / 软建议** | 硬约束 = 可验证的量化事实（关单率、当前负荷），规则引擎负责，永不让模型推翻；软建议 = 匹配度、话术、排序，模型负责，可被红娘一键否决。 |

# 第一部分 · 设计诊断与理念

## 1.1 一个必须先说清的事实

当前界面**不是**「缺少情绪价值」，而是**在制造情绪消耗**。它把一套严谨的履约账本，直接翻译成了人话——但那套人话是**系统的人话**，不是**红娘的人话**。

三类消耗：

1. **认知消耗**：每张卡片是一段 40+ 字的中文长句，红娘要逐句读完才知道要不要动手。
2. **术语消耗**：「待启用」「缺服务人」「落到店长，待换红娘」——这些是 `HomeKind` 的取值，是给开发看的。
3. **失控消耗**：黑底汇总块把「今天有 N 单」摆在最前面，把一天的劳动压缩成一个负债数字。

## 1.2 三层供给框架（设计的全部依据）

情绪价值不能靠「加几个笑脸 emoji」实现。它必须落在三个可验证的层面：

| 层 | 定义 | 现状 | 设计对策 |
|---|---|---|---|
| **被看见**<br>Recognition | 我的劳动被系统记得、被呈现 | 只有负债数字（待办 14 单） | 成就带：陈述**今天你帮了谁**，而非今天你还欠多少 |
| **有掌控**<br>Agency | 我知道下一步做什么，做了立刻有反馈 | 动作藏在弹窗里，写完还要自己 reload 判断成没成 | 卡片上直接放主动作；写入后原地更新 + 明确回执 |
| **被托住**<br>Support | 我不用记住所有细节、不用怕漏事、不用自己造句 | 全靠人脑；AI 按钮是假的 | AI 起草（可编辑、不覆盖、确认后才落账）+ 主动信号提醒 |

> 类比：现在的界面像**医院的病历系统**——准确、冷硬、以「未完成」为中心。目标界面像**一间好的咨询室**——进门先被照顾，然后才开始工作。

| 空状态是「没有 X」 | 「今天没有待办」 | 「今天没有要赶的事。要不要看看这 3 位好久没联系的会员？」 |

# 第二部分 · 体验设计方案

## 2.1 信息架构：两层，而不是三层

现状首屏是 `待判断 / 例外 / 审核` 三个平级 tab。红娘的一天不是按「系统模块」分的。

```
第一层 · 今日（默认首屏，占 80% 注意力）
    ├─ 今日叙事头：一句人话 + 成就带
    ├─ 要紧（约会结果 / 到期 / 恋爱确认）
    ├─ 要回应（超时未联系 / 待确认推荐草稿）
    └─ 要点头（赠送 / 暂停 / 关单待审 —— 只在有审核权限时出现）

第二层 · 业务（左侧导航收进去，不再占首屏）
    ├─ 服务库（今天的人）
    ├─ 会员（点卡片直达）
    ├─ 审核（= 今天的「要点头」的完整版）
    └─ 过期 VIP
```

**关键变化**：三 tab 变两 tab。原来的「待判断 + 例外」合并为「今日」的**语义分组**（按紧急度而非按系统来源），原来的「审核」降为「要点头」的分组视图。

> 注意：这是**纯读模型重组**。`src/home.ts` 的 `judgement / exceptions / reviews` 三个数组继续照旧产出，前端按映射表重排即可，不需要动域层。

分组映射表（前端新增一个函数即可）：

| 新分组 | 来源 kind | 紧急度 | 主文案模板 |
|---|---|---|---|
| 要紧 | `见面结果`、`起草关单`、`关单建议` | 高 | 「周晚宁 · 结果还没落上」 |
| 要回应 | `推荐草稿`、`换人`、`开启缺口` | 中 | 「苏念 · 3 天没联系」 |
| 要点头 | `赠送`、`暂停`、`关单` | 中 | 「许知夏 · 赠送待你点头」 |
| 待安排 | `要暂停`、`要赠送`、`提前关单`、`提前恢复` | 低 | 「陈见鹿 · 可以提前恢复」 |

## 2.2 六个核心组件

### 组件 1 · 会员优先卡片（Member-First Card）

```
┌────────────────────────────────────────────────────────┐
│  ⬤ 周晚宁                    VIP · 已婚 3 天      ⋯     │
│  已见面 · 双方都还想再见一面                              │  ← 标题 ≤12 字
│  ─────────────────────────────────────────────────────  │
│  [ 写清见面结果 ]  [ 打开档案 ]                           │  ← 主动作在卡片上
└────────────────────────────────────────────────────────┘
     订单 205 · 2026-09-20 · 门店会客室（默认收起）          │  ← ID 降为角标
```

- 主视觉：**头像 + 姓名**（复用 `MemberAvatar`），不是订单号
- `订单 / 会议 / 门店` 全部收进第二行小字，鼠标悬停或点击展开
- 右上角是一个**状态语气**而不是状态枚举：`VIP · 已恋爱 3 天` 而非 `status=启用中`

### 组件 2 · 两段式摘要

- **主文案**：≤12 字，动词开头，给出「现在该干嘛」
- **正文**：点开才看，完整语境 + 「系统怎么算的」折叠区
- 实现上把现在 `HomeItem.detail` 拆成 `summary`（新增字段，前端生成）+ `detail`（保留原文）

### 组件 3 · AI 起草块（AI Draft Block）

这是**信任设计的核心**。规则：

1. AI 生成的内容**不进输入框**，先显示为独立草稿块，带明确标识 `AI 起草 · 你可以改`
2. 只填**还空着的**项（沿用现有 `isUnwritten()`：空字符串、或 `reason === STUB_REASON` 才算空）
3. **永不覆盖**已写内容
4. 每个字段旁边一个 `用这段` 的轻按钮 → 点了才填进输入框
5. 顶部一个 `全部采用`，但下面永远有一句小字：`这是 AI 写的，红娘以你的话为准`
6. 失败时**不弹错误**，静默回退到本地写法，并标注 `这次没调通，已用本地写法`

> 为什么不用流式直接写入输入框：输入框里的文字 = 我的署名。署名不能被机器悄悄改掉。这条是不可协商的。

### 组件 4 · 成就带（Achievement Ribbon）

把「今天的三块：14 单 / 5 单 / 4 单」换成**事实陈述**：

```
今天  3 位会员确认恋爱  ·  2 场见面完成  ·  1 份服务到期完成  ·  你联系了 7 位会员
```

- 数据全部**已存在**：`meetings.result`、`applications.status`、`notes` 条数
- **不改域模型**，纯读模型派生（新增 `GET /api/home` 的 `todayFacts` 字段，或前端从现有数据算）
- 视觉：暖色渐变带，圆角 16px，替代现在的死黑块

### 组件 5 · 温柔空状态

| 场景 | 现在 | 改成 |
|---|---|---|
| 今天没有待办 | 「今天没有待确认的推荐、到点的见面、到期起草的关单，也没有已恋爱的关单建议。」 | 「今天没有要赶的事。要不要看看这 3 位好久没联系的会员？」+ 按钮 |
| 服务库为空 | 「这位服务人名下现在没有待开启或服务期内的会员…」 | 「你手上现在很轻。要不要接一位刚成交的会员？」 |
| 审核为空 | 「没有待审的赠送。」 | 「没有等你点头的事，都批完了。」 |

> 空状态是唯一「零成本触达用户」的位置，必须给**下一步动作**，而不是否定句。

### 组件 6 · 情绪安全网

- **高风险动作前置人话确认**：`确认开启` → `开启后，周晚宁 就是正式在服务中`，而不是「确定吗？」
- **不可逆动作给撤销窗口**：关单二审通过后 10 秒内可撤销（前端层面，服务端已落账 → 需要后端出一个 `reviewCloseSecond` 的补偿写入 `revertClose`，⚠️ 见第五部分风险）
- **写完立刻回执**：`已写入推荐 · 周晚宁 × 林澄`，而不是静默 reload

## 2.3 视觉语言（Design Tokens）

现状色板偏冷、偏后台系统。改动的原则：**结构用靛蓝，温度用暖色**——两个语义色分工明确，不混用。

| Token | 现值 | 新值 | 语义 |
|---|---|---|---|
| `--color-primary` | `#5B55D6` | `#5A5FC7`（降饱和） | **结构**：导航、选中态、链接 |
| `--color-care`（新） | — | `#E8735A`（暖珊瑚） | **温度**：AI 建议、关怀提醒、成就 |
| `--color-celebrate`（新） | — | `#D99A2B`（暖金） | 成就带强调、恋爱确认 |
| `--color-warn`（新） | — | `#D9A441` | 逾期/待办（**不用红**） |
| `--color-surface` | `#F6F5F2` | `#FAF7F2`（更暖的米） | 背景 |
| `--color-ink` | `#252523` | `#2A2622`（暖黑） | 正文、暗色块 |
| `--shadow-card` | 中性灰 | `0 6px 24px rgba(232,115,90,.07)` | 卡片阴影带暖 |

**字体**：正文保持 `--font-sans`；**大标题新增衬线** `Noto Serif SC / 思源宋体`，字号 30→36px。中文衬线在「温度」上的增益非常显著，是低成本高回报的一改。

**动效**（克制）：
- 卡片进入：`opacity 0→1 + translateY 6px`，160ms，`cubic-bezier(.2,.7,.3,1)`
- AI 草稿块：`渐显`，不做打字机效果（打字机在工具里是噪音）
- 成就带数字：`countUp` 400ms，仅首次挂载
- 全局遵守 `prefers-reduced-motion: reduce` → 全部降为 0ms

## 2.4 交互规范（5 条，写进 Code Review）

1. **一次点击直达动作**——卡片上必须有主动作按钮，不允许「先点进详情再找按钮」
2. **系统给草稿，人做决定**——AI 永不自动提交，永不覆盖已写内容
3. **不制造恐慌**——暖黄=需要注意，暖珊瑚=需要你行动，红色=真的错了
4. **零空状态必须是机会**——每个空状态带一个主动作
5. **术语只出现一次**——系统术语（启用中/待启用/待二审）只在「详情」里出现一次，标题层用口语

## 2.5 可访问性（红线）

- 正文最小 12px；长文案 `line-height ≥ 1.6`（现在 `leading-5` 偏紧）
- 卡片 `tabIndex=0`，支持 `j/k` 上下切换、`Enter` 触发主动作——红娘一天处理几十条，键盘流是刚需
- 所有色彩语义必须有非颜色冗余（图标/文字），不能只靠颜色区分
- 头像 `alt` 写姓名（现在 `MemberAvatar` 的 `alt=""` 是空 alt，屏读器读不到人名，**这是可访问性缺陷，建议一并修**）

# 第三部分 · AI 能力实施方案

## 3.1 先说实话：两个「AI」现在都是假的

| 入口 | 位置 | 现在实际是什么 | 问题 |
|---|---|---|---|
| 「AI 补写」按钮 | `web/src/draftCopy.ts` `suggestRecommendationCopy()` | 4 组写死话术，按 `seed % 4` 取一条 | 界面承诺 AI，交付模板——**信任透支** |
| 「AI 推荐理由」 | `web/src/staffScore.ts` `scoreServicePeople()` | 规则加权：关单率 35% + 负荷 25% + 状态 20% + 业绩 20% | ① 不是 AI；② 只有聚合指标，**没有会员画像匹配度**——给「刚失恋需要倾听」和「需要成熟稳重沟通」的会员，它排序完全一样；③ `reason` 是模板句，零信息增量 |

**好消息**：两个功能的 UI 入口、权限位、调用时机**都已经就位**。我们要做的不是加功能，是**把这两个位置的脑子换掉**。

## 3.2 前置阻塞项：会员画像缺失（必须先解决）

`members` 表只有 6 列：

```ts
{ id, tenantId, shopId, maturity, memberType, createdAt }
```

**没有姓名、年龄、城市、职业、生活节奏、情感诉求、禁忌点。** 展示名现在硬编码在前端 `web/src/memberProfile.ts` 里。

> 结论：**在这张表补齐画像之前，AI 推荐语只能生成泛化套话，价值接近于零。** 这是唯一的硬前置。

### 方案对比

| | 方案 | 内容 | 优点 | 缺点 |
|---|---|---|---|---|
| **A（推荐）** | 新增 `member_profiles` 主档表 | 与 `members` 1:1：姓名、年龄、城市、职业、作息、情感诉求、优势自述、禁忌点、可披露边界 | 是真正的 CRM 主档，直接喂两个 AI 能力 | 需迁移 + 种子数据；**采集入口要设计**（谁填？红娘填？还是从成交域同步） |
| B | 不建表，只用现有信息 | AI 只知道「同在服务库 + 历史推荐记录」 | 零改动 | 生成结果只能是「两人都在服务库，建议先见一面」，红娘不会用第二次 |
| C | AI 从对话里猜 | 让模型凭空推断会员性格 | 零改动 | **不可接受**：编造事实，用来对客户描述他人 |

**建议 A**，并且它天然不违反本项目的信条——「一笔订单一条服务实例」约束的是**履约账**；`member_profiles` 属于 **CRM 客户主档**域，是另一个边界清晰的域。

## 3.3 AI 通道设计

```
┌─ web/ ────────────────────────────────────────────────┐
│  卡片上的「AI 起草」按钮 / 「谁更适合」面板              │
│    ↓ POST /api/actions/suggest-recommendation-copy     │
│    ↓ POST   /api/suggest-staff-fit                     │
└────────────────────────────────────────────────────────┘
                         ↓  红娘权限校验（复用现有 MATCHMAKER_PATHS）
┌─ src/http.ts ─────────────────────────────────────────┐
│    只做鉴权 + 参数校验 + 组装上下文，不含 prompt        │
└────────────────────────────────────────────────────────┘
                         ↓
┌─ src/ai/ ─────────────────────────────────────────────┐
│  provider.ts   chatJson()  超时/重试/JSON 解析/降级      │
│  prompts/*.ts  prompt 模板 + 版本号 + 输出 schema      │
│  cache.ts      inputHash → Redis，命中不重复计费        │
│  audit.ts      ai_invocations 落库（用途/模型/耗时/token）│
└────────────────────────────────────────────────────────┘
                         ↓  fetch  OpenAI 兼容协议
                 DeepSeek / 智谱 GLM / 通义 / 本地 vLLM
```

### 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 走什么协议 | **OpenAI 兼容 `/chat/completions`** | 一套代码切模型，只需改 `baseURL` + `model` |
| AI 结果写不写库 | **不写。全部只返回前端预览** | 保持「确认后才写推荐事实」的域约束不变；AI 挂了也不污染数据；可随时回滚 |
| 模型能不能推翻硬约束 | **不能** | 服务人推荐里，规则分是硬约束，模型只重排 + 解释 |
| 失败怎么办 | **静默降级到现有规则文案**，UI 标注「这次没调通，已用本地写法」 | 红娘不该在情绪高压时看到技术错误 |
| Key 放哪 | **只在服务端 `src/ai/`**，`.env` 注入（已在 `.gitignore`） | 绝不下发到 `web/` |
| 温度 | 推荐语 `0.7`（要自然）；服务人匹配 `0.2`（要稳定可复现） | — |

### `.env` 新增配置

```dotenv
AI_ENABLED=0                 # 总开关。0 = 全走现有规则逻辑，离线可跑测试
AI_BASE_URL=https://api.deepseek.com/v1
AI_API_KEY=
AI_MODEL=deepseek-chat
AI_TIMEOUT_MS=8000
AI_MAX_RETRY=2
AI_CACHE_TTL_SECONDS=86400
```

## 3.4 模型选型

| 供应商 | 协议 | 相对价格 | 中文质量 | 适合场景 | 判断 |
|---|---|---|---|---|---|
| **DeepSeek** | OpenAI 兼容 | 最低档 | 好 | 批量高频生成 | ✅ **主力**。推荐语是高频批量，便宜是硬需求 |
| **智谱 GLM-4-Flash** | OpenAI 兼容 | 有免费额度 | 好 | 主力备选 / 成本兜底 | ✅ **备选**（免费额度用完自动切） |
| 通义 qwen-plus | DashScope（需 SDK 适配） | 中 | 很好 | 已有阿里云账号时 | 🔸 备选，接入成本略高 |
| OpenAI / Claude | 原生 | 高 | 好 | 复杂推理 | ❌ 不适合批量文案场景 |

**结论**：`AI_BASE_URL` + `AI_MODEL` 双配置，主 DeepSeek、备 GLM-4-Flash，配置化切换，不锁死。

## 3.5 特性一 · AI 推荐语自动写入

### 输入上下文（全部来自域层已存在的数据 + 新增画像）

| 来源 | 内容 |
|---|---|
| `member_profiles`（新） | 会员画像 A、嘉宾画像 B |
| `recommendations` / `meetings` / `notes`（已有） | 历史推荐、见面结果、人工小记里的偏好线索 |
| `orders` / `service_instances`（已有） | 服务时长、剩余次数、当前状态 |
| `careSignals()`（已有） | 「超过7天未联系」「新分」「确认恋爱」 |

### Prompt 要点

- **System**：你是资深红娘助理，帮红娘写**给红娘自己看**的推荐说明草稿。语气温和、具体、不油腻、**不承诺结果**。**只使用给定信息，禁止编造会员没说过的属性**。
- **User**：结构化 JSON（画像 A、画像 B、共同点、差异点、历史线索）
- **Output**：严格 JSON `{ progress, reason, highlights, hiddenPoints }`，每字段 ≤ 60 字
- **护栏**：不得出现联系方式/价格/成功率承诺；不得给未提供的属性贴标签；输出必须能被 `JSON.parse` 且通过 zod 手写校验，失败重试 1 次后降级

### 前端交互（组件 3 落地）

```
确认推荐
┌────────────────────────────────────────────────┐
│  ✨ AI 起草 · 你可以改            [全部采用] [换一版] │
│  ────────────────────────────────────────────── │
│  进度     │ 已把林澄介绍给周晚宁，还没约见面       │
│  理由     │ 两人都在成都，作息都早，周末常去...   │  [用这段]
│  亮点     │ 林澄表达直接，作息稳定。               │  [用这段]
│  需要隐瞒 │ 先别提她上个月那次没约成的原因。       │  [用这段]
│  ──────────────────────────────────────────────  │
│  这是 AI 写的，红娘以你的话为准。                  │
└────────────────────────────────────────────────┘
```

- `换一版` = 同一 prompt、`seed` 变化、`temperature=0.9`
- 全部字段可编辑；编辑过的字段 `AI 起草` 标记消失
- 顶部保留：已写的项显示 `✓ 你已经写过了，AI 不会动它`

### 验收标准

| 指标 | 门槛 |
|---|---|
| 编译性 | 输出 100% 可 `JSON.parse`，字段完整率 100% |
| 事实性 | 盲评 20 组，**0 次**编造画像中不存在的属性 |
| 有用性 | 盲评中 AI 草稿优于模板话术的比例 ≥ 70% |
| 可控性 | `全部采用` 之后，红娘手动修改比例 ≤ 30%（说明草稿够好） |
| 降级 | 断网/超时 → 自动回退本地写法，UI 提示，无堆栈报错 |

## 3.6 特性二 · AI 服务人推荐

### 两段式：规则打底 + 模型补充

| 阶段 | 负责 | 内容 |
|---|---|---|
| **Stage A（保留现有）** | 规则引擎，**不可被推翻** | `scoreServicePeople()`：关单率、在服负荷、暂停占比、通过关单业绩 |
| **Stage B（新增模型）** | 模型，**只重排 + 解释** | 画像匹配度 `fitScore`、为什么合适 `whyMatch`、**为什么不合适** `risk`、一句话开场 `firstTalk` |

### 为什么这个设计更靠谱

- 关单率、当前负荷是**可验证的量化事实**，让模型算反而不可靠且不可审计
- 真正缺的是**匹配维度**（画像 ↔ 画像）和**可执行落点**（开场话），这两件事规则做不了
- `risk` 字段是关键：**告诉红娘「不选谁、为什么不选」**，这比只推一个答案有用得多

### 输出 Schema

```ts
{
  personId: number;
  fitScore: number;        // 0-100，仅用于排序，Stage A 硬约束仍生效
  whyMatch: string;        // ≤50 字，为什么这位更合适
  risk: string;            // ≤40 字，需要注意什么
  firstTalk: string;       // ≤60 字，可直接发给会员的开场
}
```

### 前端交互（`AssignDialog` 重做）

```
谁接这一单？                                    林晓 只能看红娘
─────────────────────────────────────────────
✨ 最合适
  陈见川  红娘                              匹配度 92
  擅长：慢热会员、离婚后再婚
  为什么：他手上 4 位在服，都是慢节奏；近 3 个月
        经手的 5 位会员有 2 位在 60 天内确定关系
  注意：本周已接 2 位新分，负荷偏紧
  开场：「周晚宁，上次你说想找性格稳一点的——我这边
        有位陈老师，做情感咨询 6 年，他想认识一下。」

其他人选
  许清禾  红娘                              匹配度 67
  赵衡    店长                              匹配度 41  ⚠ 建议换红娘
```

**性能要求**：不能因为等模型把首屏拖慢 2 秒。
→ `GET /api/service-people` **先同步返回规则分**，AI 结果通过**异步补全**（返回后 3~5s 轮询或 SSE），到达后原地更新。`AI_ENABLED=0` 时永远是规则分，零延迟。

## 3.7 AI 成本与稳定性

| 项 | 策略 |
|---|---|
| Token 成本 | 画像先结构化成 JSON 再进 prompt，**不要把整段历史塞进去**；推荐语一次输出约 300 token |
| 缓存 | `sha256(prompt + 上下文)` → Redis（已就位），TTL 24h。同输入不重复付费 |
| 降级链 | 模型 → 缓存 → 本地规则文案。三级，逐级回退，任何一级都不能抛错到 UI |
| 限流 | 单账号 QPS 限制，防刷；批量场景走队列 |
| 隐私 | 可配置脱敏；**日志绝不打印 `AI_API_KEY` 与完整 prompt**；`ai_invocations` 表只存 hash 和用量 |
| 审计 | `ai_invocations(用途, 模型, prompt_version, 耗时, token, 是否被采纳, input_hash)` |

# 第五部分 · 风险与边界

| 风险 | 等级 | 处置 |
|---|---|---|
| **编造会员信息** —— AI 描述了画像里没有的属性，且被红娘发给客户 | 🔴 最高 | prompt 硬约束 + 输出校验 + 只允许引用输入字段；**这一条不通过就不上线** |
| **隐私外泄** —— 客户资料发给第三方模型 | 🔴 高 | 只发结构化必要字段；提供脱敏开关；日志不落原文 |
| **回滚成本** | 🟢 低 | `AI_ENABLED=0` 一键关闭，全部退回现有规则行为；AI 结果从不写库，无需数据回滚 |
| **延迟拖垮首屏** | 🟡 中 | 服务人推荐异步补全；推荐语只在用户点击后触发 |
| **测试套件本身是坏的** | 🟡 中 | `test/fulfillment.test.ts`、`test/home.test.ts` 当前是**语法损坏**状态，`http.test.ts` 无法解析。**P0 之前应先修测试护栏**，否则 AI 改动没有回归保障 |
| **会员画像采集落不了地** | 🟡 中 | P0.5 的采集入口是产品问题不是技术问题。若短期拿不到画像，先做 P2（服务人推荐不需要新画像也能用已有指标），把 P1 押后 |
| **关单二审撤销** | 🟢 低 | 需要新增补偿写入 `revertClose`，会打破「关单通过即不可逆」的域承诺 → **本期不做**，见下 |
